# HsBaSlicer Wiki Maintenance Guide (EN/ZH Parity & Effective-Content Maximization)

[中文版本](../zh/wiki_maintenance_guide.md)

This guide defines how to maintain the project Wiki so that the **Chinese (`zh`) and English (`en`)
content stay parallel** and the published GitHub Wiki **maximizes effective information density**.
The Wiki source is `.qoder/repowiki/{en,zh}` generated by Qoder IDE, flattened by
[`scripts/repowiki_to_github_wiki.py`](../../scripts/repowiki_to_github_wiki.py) and published by
[`.github/workflows/publish-wiki.yml`](../../.github/workflows/publish-wiki.yml). The hard constraints for regeneration
are injected through the official pre-generation config
[`.qoder/repowiki/wiki_plan.yaml`](../../.qoder/repowiki/wiki_plan.yaml) (see the
[Repo Wiki docs](https://help.aliyun.com/zh/lingma/repo-wiki), "Intervene in Wiki generation"): `repowiki.notes` /
`knowledgecard.notes` carry parity, dedup and effective-content standards, `scope.exclude` trims noise, and
`repowiki.template` is set to `architecture`.

## 1. Current problem (why EN and ZH are not similar)

| Aspect | EN (96 pages) | ZH (116 pages) |
|--------|---------------|----------------|
| Top-level categories | 10 categories + 1 root loose page | 8 categories + 4 root loose pages |
| Taxonomy | Advanced Features / API Reference / **Architecture Overview** / Core Concepts / **Core Library Documentation** / Development Guide / Examples and Samples / **Lua Scripting System** / Platform Integration / Troubleshooting and FAQ | 部署和维护 / 高级主题 / 核心概念 / 核心模块详解 / 集成指南 / 扩展开发指南 / 示例和教程 / API 参考文档 |
| Root loose pages | `Getting Started.md` | `附录.md`, `贡献指南.md`, `快速开始.md`, `项目概述.md` |

Root causes:

1. **Different category skeletons.** EN has dedicated `Architecture Overview`, `Core Library
   Documentation`, `Lua Scripting System` categories that ZH lacks; ZH has `部署和维护` and
   `扩展开发指南` that EN scatters elsewhere.
2. **Unequal page counts (96 vs 116)** — ~20 pages cannot be paired 1:1.
3. **Intra-ZH duplication** — `网格模型实现` appears under both `核心概念/模型抽象接口` and
   `核心模块详解/模型处理系统`; `填充算法` appears under both `核心模块详解/2D 几何算法` and
   `核心模块详解/填充系统`. Duplicate pages dilute effective content.
4. **Root loose pages float outside categories** — the publisher's sidebar grouping relies on
   "folder name == index page title"; loose roots land in *uncategorized* and break sidebar symmetry.

## 4. Effective-content standards (maximize information density)

Every page MUST:

1. Start with a **single `# H1`** title — the publisher uses the first H1 as the sidebar link text.
2. Contain **code-grounded facts**: real function signatures, config fields, and defaults read from
   source (e.g. `pipelinetypes/pipeline_types.h`, each `*_pipeline.h`, `LuaSupport.cpp`,
   `PolygonFill.cpp`). **Never invent APIs or defaults.**
3. Include at least **one mermaid diagram or one table** that adds signal, not restatement.
4. Be **non-stub**: a page with < ~30 meaningful lines should be merged upward, not kept standalone.
5. Cross-link in its footer to the sibling-language page (`Home` ↔ `Home-zh` is auto-generated;
   page-level links must be added manually).

Publish-time noise handling: source may keep repowiki's own `<cite>`, `**Section sources**`,
`**Diagram sources**`, and `file://` links — [`clean_content`](../../scripts/repowiki_to_github_wiki.py)
strips/downgrades them at publish time. **Do not add** other noise the cleaner cannot recognize.

## 5. Page 1:1 pairing and naming

- `en/content/<Cat>/<Page>.md` must have a sibling `zh/content/<对应分类>/<对应页>.md`; totals must match.
- Keep an EN↔ZH filename map so flattened wiki page names stay addressable across languages.
- A category index page's H1 == folder name (the script detects grouping via the `X/X` repetition or a
  common prefix); otherwise sidebar grouping breaks.

## 6. Regeneration and publish workflow

1. **In Qoder IDE**, edit `.qoder/repowiki/wiki_plan.yaml` (the official pre-generation config), then pick each target
   language (en / zh) in the language dropdown and trigger "Generate / Regenerate"; changes to `wiki_plan.yaml` only take
   effect after a **manual** regeneration (the CLI cannot generate it). Post-generation, the `/knowledge` command can
   locally modify / supplement / rewrite existing pages, and manual edits are marked and protected from being overwritten
   by the next automatic update.
2. Verify parity with the checklist below before committing.
3. `git add .qoder/repowiki` → commit → push to the working branch.
4. Merge to `master`; `publish-wiki.yml` auto-publishes the flattened wiki to GitHub Wiki.

### Verification checklist

- [ ] `en` page count == `zh` page count
- [ ] every unified category exists on both sides, each with an index page
- [ ] no duplicated concept across categories (especially `网格模型实现` / mesh model impl, `填充算法` / fill algorithm)
- [ ] no floating root loose pages
- [ ] each page starts with a single `# H1`, has ≥1 diagram/table, content is code-grounded
- [ ] dry run: after `python scripts/repowiki_to_github_wiki.py --lang both --src .qoder/repowiki --out wiki-output`,
      confirm `wiki-output/_Sidebar.md` and `_Sidebar-zh.md` groupings are symmetric

Quick PowerShell to compare top-level categories and page counts on both sides:

```powershell
foreach ($l in 'en','zh') {
  Write-Output "==== $l ===="
  Get-ChildItem ".qoder/repowiki/$l/content" | ForEach-Object {
    if ($_.PSIsContainer) { "{0,-40}{1}" -f $_.Name, (Get-ChildItem -Recurse -Filter *.md $_.FullName).Count }
    else { "{0,-40}1" -f "[root]$($_.Name)" }
  }
}
```

## 7. `/knowledge` intervention playbook (fix the current wiki WITHOUT regenerating)

`/knowledge` supports four operations — **generate / modify / supplement / rewrite** — and manual edits are
marked and protected from being overwritten by the next automatic update. Invoke `/knowledge` in the input box,
paste the prompts below, and optionally attach `.qoder/repowiki/wiki_plan.yaml` or this guide as a reference file.

> **Strategy correction**: the EN category-name Chinese pollution and root loose pages are **already fixed**
> (EN is now 128 clean English-only pages, content intact). Going forward we use **neutral merge**: keep the more
> complete side per category, **delete neither side**, and bring the weaker side up to one unified structure.

### A. Use the stronger side as baseline, enrich the weaker side

- **ZH-stronger categories** (Core Concepts 22, Lua 32, API 36, Extension 8): enrich **en** —
  > Using the corresponding zh category's page list as baseline, supplement/rewrite substantive English pages missing
  > in en so this category's leaf pages pair one-to-one across languages.
- **EN-stronger categories** (Core Modules 40, Examples 18, Advanced 9, Integration 14): enrich **zh** —
  > Using the corresponding en category as baseline, supplement/rewrite substantive Chinese pages missing in zh.
- **Both-single-page categories** (Overview/Architecture/Dev-Test/Deployment/Appendix): keep concise; do not force-split.

### B. Merge only genuinely thin pages (not "delete just because a side has more pages")

> Merge or delete a page only when it is < ~30 meaningful lines and largely overlaps a sibling. If ZH's API/Lua pages
> are substantive and more complete, they are the **baseline side** and should be used to enrich EN — not trimmed away.

### C. Shared constraints to append to every `/knowledge` call

- Each page starts with a single `# H1`; body is code-grounded; at least one diagram/table per page; footer cross-links
  the sibling-language page.
- After all fixes, re-run the section 6 comparison script; expect `en count == zh count`, symmetric categories, no root loose pages.
