## 1. 使用的系统与工具

仓库没有统一的 `config/` 目录或 `.env` 文件加载器，而是把“配置”拆成两个独立子系统：

- **运行时应用配置（AppConfig）**：`utils/app_config.{hpp,cpp}` 中的 `AppConfigSingletone` 是一个线程安全的懒加载单例，通过 `shared_mutex` 保护，对外暴露 `GetSevenZPath()` 等进程级设置。它不读取任何外部配置文件，字段在内存中初始化。
- **工艺管线参数持久化（ParamStore）**：`fileoperator/param_store.{hpp,cpp}` 配合 `param_schema.hpp`、`param_reflect.hpp`、`param_convert.cpp`，将每个 PipelineConfig C 结构体（FDM/SLA/SLS/SLM/LOM/TDP/WAAM/Custom/FileTransfer）通过反射映射为 SQL 宽表行，支持 SQLite / MySQL / PostgreSQL 三种后端。
- **结构化数据序列化**：`utils/struct_json.hpp`、`utils/struct_yaml.hpp`、`utils/struct_xml.hpp` 提供基于 Boost.PFR 与 `base/static_reflect.hpp` 的通用 JSON/YAML/XML 编解码，供 ParamStore 内部及上层使用。
- **日志配置**：`logger/logger.cpp` 在启动时从当前目录下的 `logcfg.ini` 读取日志级别与输出目标；该文件由 `utils/logcfg.ini` 提供默认值。

依赖库：RapidJSON（JSON）、yaml-cpp（YAML）、TinyXML2（XML）、Boost.PFR（聚合类型反射）、cipher（AES-256-CBC 可选加密）。未引入 TOML 或环境变量解析框架。

## 3. 架构与设计决策

### 3.1 应用配置单例（AppConfigSingletone）
- 通过 `GetInstance()` / `DeleteInstance()` 控制生命周期，内部用 `std::shared_mutex` 实现读锁（`GetSevenZPath`）与写锁（构造/销毁）分离。
- 仅持有少量字符串字段（如 `sevenZ_path_`），不提供文件/环境变量加载逻辑——调用方负责在进程启动时填充。
- 单元测试覆盖双检锁多线程场景与重复 `DeleteInstance` 的安全幂等性。

### 3.2 参数持久化管道（ParamStore）
- **反射驱动**：`param_reflect.hpp` 对每种 `HsBa*PipelineConfig_t` 结构体定义 `GetTypeInfo<T>()`，用 `HSBA_PARAM_FIELD` 宏逐个登记字段名与偏移，再由 `AnyObject::ForeachField` 遍历。
- **Schema 推导**：`ParamSchema::forConfig(TypeInfo*)` 缓存每个 Config 类型的列定义，按 `ColumnKind`（Double/Int64/Text）映射到各后端的 REAL/BIGINT/TEXT。
- **Save 流水线**：Validate → Reflect → Coerce → (可选) Encrypt → Upsert，每步通过 `Raise(percent, stage)` 触发进度回调。
- **加密模式**：`SetCryptoKey()` 启用后，所有非元数据列折叠进 `param_blob` 二进制列，使用 AES-256-CBC 加解密；`param_key`、`schema_version`、`created_at`、`updated_at` 始终明文以便查询。
- **事务批量**：`SaveBatch` 显式发出 `BEGIN`/`COMMIT`/`ROLLBACK TRANSACTION`（PG 省略 TRANSACTION 关键字），失败时回滚并抛出原始异常。
- **错误传播**：`Guard` 包装所有公共方法，捕获 `RuntimeError` 写入 `last_error_` 后重新抛出，保证 Lua 层也能感知错误。

### 3.3 序列化层
- JSON/YAML/XML 三套头文件模板完全对称：均提供 `to_*` / `from_*`、`write_*` / `read_*`、`*_from_file` / `*_from_string` 接口。
- 同时支持三类类型：
  - `Reflectable<T>`（通过 `StaticReflect::Reflector` 编译期反射）
  - `Aggregte<T>`（通过 Boost.PFR 运行期反射聚合类型）
  - 自定义 `RapidJsonValueConvertible` / `YAMLValueConvertible` / `TinyXmlConvertible` concept 的类型
- 枚举统一通过 `EnumName` / `EnumFromName` 以字符串形式序列化。

### 3.4 日志配置
- `logger/logger.cpp` 在初始化时拼接 `current_path()/"logcfg.ini"` 作为日志配置文件路径。
- 该 INI 文件位于 `utils/logcfg.ini`，是仓库中唯一被代码直接读取的配置文件。

## 4. 约定与约束

- **新增 PipelineConfig 必须做三件事**：在 `pipelinetypes/pipeline_types.h` 声明 C 结构体；在 `param_reflect.hpp` 添加 `GetTypeInfo<HsBaXxxPipelineConfig_t>()` 并用 `HSBA_PARAM_FIELD` 登记每个字段；必要时在 `TypeShortName` / `DefaultTableName` / `TagOf` 中添加短名映射（见 `param_store.cpp` 中对 `HsBa*PipelineConfig` 名称的后缀裁剪与 `filetransfer` 特例）。
- **字段类型限制**：ParamStore 只接受 Double/Int64/Text（`const char*`）三种 `ColumnKind`；新增字段若为非 POD 类型需先在 `param_convert` 中增加 `FieldToAny` / `AnyToField` 重载。
- **表命名约定**：默认表名为 `hsba_param_<short_name>`，其中 short name 由类型名去掉前缀 `HsBa`、后缀 `PipelineConfig` 并转小写得到（`TypeShortName`）。
- **元数据列不可变**：`param_id`、`param_key`、`schema_version`、`created_at`、`updated_at`、`param_blob` 由 schema 层固定注入，用户不得通过反射字段覆盖。
- **加密一致性**：已加密行的 Load/Update 必须传入相同 `crypto_key_`，否则抛 `SQLAdapterQueryError("row is encrypted but no crypto key is set")`；不同密钥之间数据不可互读。
- **错误语义**：ParamStore 的所有公开方法都不吞错——`Guard` 会记录 `last_error_` 但继续抛出原异常；Lua 绑定层应检查 `GetLastError()`。
- **AppConfig 线程安全**：`AppConfigSingletone` 的 GetInstance 使用双重检查锁定 + `std::shared_mutex`，DeleteInstance 可重复调用且幂等；测试验证了 8 线程并发下返回同一实例。
- **日志配置位置**：日志 INI 文件名硬编码为 `logcfg.ini`，路径为程序当前工作目录；修改默认值需同步更新 `utils/logcfg.ini`。
- **无环境变量/命令行配置**：仓库未发现 `getenv`、`std::optional<std::string>` 形式的 CLI 参数解析或 `.env` 加载逻辑；运行时配置主要通过 API 调用（`SetCryptoKey`、`SetProgressCallback`、`SetMigrationHook`）注入。
- **无 TOML 支持**：尽管存在 `StructToml` 测试目录占位，但未发现实际 TOML 解析实现；现有序列化能力仅限于 JSON/YAML/XML。
