Thin C ABI layer built as SHARED (Windows/Linux/macOS) or STATIC (iOS) per `CMakeLists.txt`, linking against `LibHsBaSlicer` plus sibling libraries (`HsBaPipelineTypes`, `HsBaPreprocess`, `HsBaSupport`, `HsBaPaths`, `HsBaVersion`, `HsBaSlicerConverter`, `HsBaSlicerProto`) but never calling them directly — only via their exported functions, as enforced by the build manifest comment. Internal structure:
- ABI surface: `dllexport.h` defines `HSBA_SLICER_API` (Windows `__declspec(dllexport/dllimport)`, no-op elsewhere); every public symbol is wrapped in `extern "C"`.
- Entry point: `initialize.cpp` exposes `initialize()` for one-time registration of Lua functions, pipeline types, and runtime setup.
- Pipeline adapters: each printer technology has a paired `<technology>_pipeline.{h,cpp}` file (`fdm_pipeline`, `sla_pipeline`, `sls_pipeline`, `slm_pipeline`, `lom_pipeline`, `tdp_pipeline`, `waam_pipeline`) plus `custom_pipeline` for fully Lua-driven workflows; these translate between `HsBaPipelineConfig_t` / `HsBaPipelineResult_t` structs and the underlying engine.
- Cross-cutting infrastructure: `file_transfer_pipeline` and `param_store_pipeline` provide shared transport/storage abstractions used by multiple printers; `model_preprocess` handles mesh/model preparation; `pipeline_convert` bridges pipeline type conversions; `pipeline_parallel.hpp` provides parallel execution helpers.
- Extension hooks: `lua_register.h` exposes `HsBaAdd2DFunction` / `HsBaAdd3DFunction` / `HsBaAddFileFunction` / `HsBaAddEventCallback` so external code can plug custom Lua stages into the pipeline; `event_source_register.h` wires zipper and database event sources back into Lua via `HsBaAddZipperEventCallback` / `HsBaAddDBEventCallback`.
- Versioning: `version_info.{h,cpp}` exposes library version metadata to consumers.
Dependency direction is strictly outward-only: this module depends on `LibHsBaSlicer` and sibling libs but is not depended on by them.
