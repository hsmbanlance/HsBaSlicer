Two cooperating sub-trees with a one-way dependency (proto → generated code → consumers; pipelinetypes is standalone):
- `pipelinetypes/pipeline_types.h` is a header-only, `extern "C"` ABI surface: it declares per-technology config/result structs (`HsBaFdmPipelineConfig_t`, `HsBaSlaPipelineConfig_t`, `HsBaSls/Slm/Lom/Tdp/WaamPipelineConfig_t`, `HsBaFileTransferPipelineConfig_t`, `HsBaCustomPipelineConfig_t`) together with matching `*Result_t` structs, progress/result callback typedefs, and `static inline HsBa*ConfigDefault()` initializers. It deliberately avoids `HSBA_SLICER_API` / `dllexport.h` so downstream modules (e.g. `convert`) can include it without linking `DllHsBaSlicer`. The `HsBaPipelineKind` enum mirrors `fileoperator/param_reflect.hpp`'s `PipelineConfigTag`.
- `proto/*.proto` defines the protobuf3 schema under package `HsbaProto`; `base_config.proto` centralises shared enums (`msg_technology_type`, `msg_support_type`, material/light/gas/output/profile-format enums) that are then referenced by the technology-specific files (`fdm_pipeline.proto`, `sla_pipeline.proto`, `slm_pipeline.proto`, `sls_pipeline.proto`, `lom_pipeline.proto`, `tdp_pipeline.proto`, `waam_pipeline.proto`, `custom_pipeline.proto`, `file_transfer_pipeline.proto`). Geometry primitives live in `point.proto`, `vector.proto`, `path.proto`, `mesh.proto`, `transform.proto`, `boolean_operation.proto`, `slice_config.proto`.
- Build: `proto/CMakeLists.txt` uses `find_package(Protobuf REQUIRED)` and `PROTOBUF_GENERATE_CPP` to build a static library `HsBaSlicerProto` from the generated `.pb.cc/.pb.h`, while also offering optional multi-language generation (C++, C#, Java, Python, PHP) into `HSBA_PROTO_OUT_DIRECTORY` via `HSBA_PROTO_OUT_*` options. `pipelinetypes/CMakeLists.txt` exposes an INTERFACE library `HsBaPipelineTypes` whose only role is to propagate include paths — no compiled code.
