Each subdirectory under `samples/` is an independent CMake target with its own `main.cpp`, `CMakeLists.txt`, and optional `scripts/` directory — there is no shared library among them.

- Per-slice-type samples (`FDM/`, `SLA/`, `SLM/`, `SLS/`, `TDP/`, `WAAM/`, `LOM/`) call a single typed pipeline API (e.g. `fdm_pipeline.h`, `sla_pipeline.h`) through `HsBaCreateDefaultConfig` / `HsBaRun*Pipeline` / `HsBaFreePipelineResult`, showing sync vs async execution, parameter overrides, and Lua plug-in hooks (`support_lua_script`, `infill_lua_script`).
- `Custom/main.cpp` is the central showcase: it drives the generic `custom_pipeline.h` entry points (`HsBaRunCustomPipeline`, `HsBaRunCustomPipelineAsync`, `HsBaCustomConfigFromProtoBytes` / `ToProtoBytes`) and demonstrates five invocation modes — script file, inline Lua source, async callback, Protobuf wire bytes, and per-machine machine tables injected via `cfg.pipeline_lua_source`. The sibling scripts under `Custom/scripts/` implement one full workflow each (`my_fdm_pipeline.lua`, `my_sls_pipeline.lua`, …).
- `LibHsBaSlicer/` shows two ways to consume the core library directly: `main_header.cpp` links `LibHsBaSlicer` via traditional headers, while `main_module.cpp` links `ModuleHsBaSlicer` via the C++20 module build path; both are built as executables on desktop and static libraries on Android/iOS.
- Cross-cutting resources: the Stanford Bunny STL lives in `FDM/models/` and is copied into every other sample's output directory by their `CMakeLists.txt` post-build commands; all samples log through `logger/logger.hpp` when `HSBA_GAME_CONSOLE` is not defined.
