- Every sample follows the same lifecycle: create default config via `HsBaCreateDefaultConfig` / `HsBaCreateDefaultCustomConfig`, populate `model_name` + `model_path`, call a synchronous `HsBaRun*Pipeline` or asynchronous `HsBaRun*PipelineAsync`, then free the result with `HsBaFreePipelineResult` / `HsBaFreeCustomPipelineResult`.
- Progress reporting uses a `OnProgress(int percent, const char* stage, void*)` callback registered with the pipeline run function, and logging goes through a local `LogMsg` helper that dispatches to `LoggerSingletone::LogInfo` unless `HSBA_GAME_CONSOLE` is defined.
- Lua-driven workflows are configured by setting `pipeline_lua_script` (or `pipeline_lua_source` for inline code) plus an `entry_func` (defaulting to `run_pipeline`); machine parameters are passed as a Lua table string in `cfg.pipeline_lua_source` so the script can read `machine = { ... }`.
- Per-printer process parameters (layer height, first layer height, fill spacing, wall count, laser power, etc.) are always supplied as a Lua table literal in `cfg.pipeline_lua_source`, keeping C++ configuration separate from the Lua workflow definition.
- Output directories are created at runtime via `std::filesystem::create_directories("output")` before any pipeline runs, and results are written to files under that directory.
