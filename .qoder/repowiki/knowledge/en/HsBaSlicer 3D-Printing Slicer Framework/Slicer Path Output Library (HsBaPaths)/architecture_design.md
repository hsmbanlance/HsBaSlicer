The module builds a single static library `HsBaPaths` (see `CMakeLists.txt`) around one abstract interface, `IPath`, which declares the uniform `Save(path)` / `ToString()` families plus overloads accepting inline Lua scripts, script files, named entry functions, and a `lua_reg` callback to expose extra bindings.

- Base hierarchy: `IPath` is implemented directly by `RobotPath`, `ImagesPath`, and `Pointspath`; `LayersPath` extends it to hold ordered per-layer `PolygonsD` groups with free-form config strings; `GCodePath` further derives from `LayersPath` to emit firmware-specific G-code (Marlin/RepRap/Klipper) including continuous spiral walls via `PathPoint3D`.
- Dependency direction inside the module: `GCodePath` → `LayersPath` → `IPath`; `WeldRobotPath` derives from `RobotPath`. Cross-module dependencies are declared in `CMakeLists.txt`: `HsBaSlicerBase`, `HsBaSlicerFileOperator`, `HsBaCipher`, `HsBaSlicer2D`, `HsBaSlicerUtils`, and `LUA_LIBRARIES` (with `target_include_directories` pointing at `${LUA_INCLUDE_DIR}`).
- The Lua integration is opt-in: every `Save`/`ToString` overload accepts an optional script string or script file path plus a `std::function<void(lua_State*)>` registration callback; `lua_State` is forward-declared in headers so the core API does not include `lua.hpp`.
- Each concrete path type owns its data (`std::vector<RLPoint>`, `std::unordered_map<std::string,std::string>` images, `std::vector<LayersData>`, `std::vector<PathPoint3D>`) and exposes brand-specific generators as private helpers (e.g. `GenerateAbbCode`/`GenerateKukaCode`/`GenerateFanucCode`, `GenerateHeader`/`GenerateFooter`/`GenerateLayerGCode`).
