The library is organized as a layered orchestration kernel sitting on top of lower-level primitives:
- `Pipeline/` defines per-process kernels (`fdm_pipeline`, `sla_pipeline`, `sls_pipeline`, `slm_pipeline`, `lom_pipeline`, `tdp_pipeline`, `waam_pipeline`) and a fully Lua-driven `custom_pipeline`; all share the native types in `kernel_types.hpp` (`GeometryCapture`, `Hooks`) so the Dll C ABI and the C++20 module call one implementation.
- Stage primitives are split by concern: `Preprocess/` (model loading), `Slice/` (mesh slicing), `Floor/` (SLA floor rings), `Fill/` (polygon infill), `Support/` (FDM supports), `Path/` (path generation, spiral path, optimizer, SLA/SLS/WAAM exporters).
- `ParamStore/` wraps `HsBaSlicerFileOperator` to persist/load `PipelineConfig` C structs into SQLite/MySQL/PostgreSQL backends via reflection; `Transfer/` handles file I/O.
- `Extends/` embeds Lua, registering the `HsBa` global table with model/slice/support/fill/path/file operations for scriptable custom pipelines (`lua_pipeline`, `LuaAddFunction`, `EventSourceFunction`, `LuaCommonTypes`).
- Build boundary: `CMakeLists.txt` builds either a static or shared lib (`BUILD_SHARED_LIBS` toggles `HSBA_SLICER_EXPORTS` + `export.h`'s `HSBA_SLICER_LIB_API` macro); public deps are `HsBaSlicerBase`, `HsBaSlicerMesh`, `HsBaSlicer2D`, `HsBaSupport`, `HsBaPaths`, `HsBaPipelineTypes`; internal-only deps are `HsBaSlicerUtils`, `HsBaPreprocess`, `HsBaVersion`, `HsBaSlicerFileOperator`, optionally `HsBaSlicerCADModel` behind `HSBA_COPL`.
- Dependency direction inside the module flows outward from `Pipeline` → stage primitives (`Preprocess`/`Slice`/`Floor`/`Fill`/`Support`/`Path`) → persistence (`ParamStore`/`Transfer`); `Extends` depends on the same primitives to expose them to Lua scripts.
