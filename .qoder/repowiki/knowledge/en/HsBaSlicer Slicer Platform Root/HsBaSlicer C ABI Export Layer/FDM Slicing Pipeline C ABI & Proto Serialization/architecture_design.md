Two complementary layers under `DllHsBaSlicer`:

- `fdm_pipeline.{h,cpp}` exposes a pure C ABI (`extern "C"`, `HSBA_SLICER_API`) with three entry points: `HsBaCreateDefaultConfig`, `HsBaRunFdmPipeline` (blocking), `HsBaRunFdmPipelineAsync` (non-blocking via C++20 coroutines + `Utils::Task`/`.then`), and `HsBaFreePipelineResult`. The synchronous wrapper calls `.get_result()` on the coroutine; the async wrapper heap-allocates an `InternalConfig` shared_ptr so it survives coroutine suspension, then invokes the user's `HsBaResultCallback` with ownership of malloc'd strings transferred to the caller.
- Internally, the pipeline is implemented as a single `RunPipelineAsync` coroutine in the anonymous namespace of `fdm_pipeline.cpp`, orchestrated through five explicit stages: Preprocess (model load via `GetModel`/`LoadModel` from `LibHsBaSlicer/Preprocess`), Slice (parallel per-layer `SliceLayer` over a shared topology built by `BuildSliceTopology`), Support (either Lua-driven `GenerateAllLuaSupport` or native `GenerateAllFdmSupport`), Fill (serial when Lua infill is used, otherwise parallel `FillWithBorder`), and Path Generation (`GenerateGCodePathV2` or spiral `GenerateGCodePathSpiral`). Progress is reported through a pluggable `HsBaProgressCallback` at each stage boundary. Parallelism uses `ParallelForLayers` from `pipeline_parallel.hpp`; Lua support/infill goes through `LuaCommonTypes` / `LuaCustomFillByFile`.
- `pipeline_convert.{h,cpp}` provides a symmetric pair of `*FromProtoBytes` / `*ToProtoBytes` functions for every pipeline technology (FDM, SLA, SLS, FileTransfer, Custom/Lua, SLM, LOM, 3DP, WAAM) plus per-type `HsBaFree*ConfigStrings` helpers. All output buffers are `malloc`-allocated and owned by the caller; return codes are `int` (1 success, 0 failure). This file is the sole bridge between protobuf wire format and the C ABI structs defined in `pipelinetypes/pipeline_types.h`.

Dependency direction: this module depends downward on `LibHsBaSlicer/*` (preprocess, slice, support, fill, path generation) and `base/coroutine.hpp`, but nothing inside `LibHsBaSlicer` depends back on these DLL export files — they are leaf consumers of the core library.
