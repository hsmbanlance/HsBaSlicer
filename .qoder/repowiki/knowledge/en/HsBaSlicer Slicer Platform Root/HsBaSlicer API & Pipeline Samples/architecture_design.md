Each subdirectory under samples/ is an independent CMake target that links against a built HsBaSlicer artifact and ships its own `main.cpp` plus optional `scripts/*.lua` resources. The layout mirrors the public surface:
- Per-process technology samples: `FDM/`, `SLA/`, `SLS/`, `SLM/`, `TDP/`, `WAAM/`, `LOM/` — each targets one `*_pipeline.h` (e.g. `fdm_pipeline.h`, `sla_pipeline.h`) and demonstrates sync (`HsBaRun*Pipeline`) and async (`HsBaRun*PipelineAsync`) execution, with per-stage Lua hooks (`support_lua_script`, `infill_lua_script`, `floor_lua_script`).
- `Custom/`: the flagship example for the fully scriptable `custom_pipeline.h` API; it exercises five invocation modes in one binary — file-based Lua scripts, inline Lua source, synchronous vs asynchronous execution, and a hand-written Protobuf wire encoder/decoder around `HsBaCustomConfigFromProtoBytes` / `ToProtoBytes`.
- `LibHsBaSlicer/`: two entry points — `main_header.cpp` linking `LibHsBaSlicer` via traditional headers, and `main_module.cpp` using `import hsba.slicer;` (C++20 module) to drive `Model` → `FdmPipeline` → `FdmResult` plus the custom Lua pipeline.

Dependency direction is strictly downward: samples depend on `DllHsBaSlicer` (C ABI), `LibHsBaSlicer` (C++ API), or `ModuleHsBaSlicer` (C++20 module); they never link the core engine directly. Build manifests copy the shared `samples/FDM/models/stanford_bunny.stl` into each target's output directory and, for non-mobile builds, also copy the relevant `scripts/` tree so the executables can load them at runtime. Mobile builds (`ANDROID`/`IOS`) switch from `add_executable` to `add_library(... STATIC)` so the code still compiles without producing a console binary.
