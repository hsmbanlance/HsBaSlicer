- Each sample follows a fixed four-step pattern: obtain default config via `HsBaCreateDefault*Config()`, set `model_name`/`model_path`, call the synchronous `HsBaRun*Pipeline()` (or `*Async` variant), then free the result with the matching `HsBaFree*PipelineResult()` before returning.
- Cross-platform logging is wrapped in a local `LogMsg` helper that dispatches to `LoggerSingletone::LogInfo` when `HSBA_GAME_CONSOLE` is not defined and no-ops otherwise, keeping game-console builds compilable without the logger library.
- Lua customization is wired through paired `<stage>_lua_script` + `<stage>_lua_func` fields on the pipeline config (e.g. `support_lua_script`/`support_lua_func`, `infill_lua_script`/`infill_lua_func`, `floor_lua_script`/`floor_lua_func`), pointing at a `scripts/my_*.lua` file and a function name such as `generate_support` or `run_pipeline`.
- Per-print machine parameters are passed as an inline Lua string via `cfg.pipeline_lua_source` (or the equivalent field per pipeline) so the script can read a global `machine` table that overrides defaults before the main script runs.
- Sample targets are conditionally compiled as static libraries on Android/iOS (`if(ANDROID OR IOS) add_library(... STATIC ...)`) and as console executables otherwise, while sharing the same source files across platforms.
